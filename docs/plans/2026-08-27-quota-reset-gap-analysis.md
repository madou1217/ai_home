# 配额重置检测与异步自动探测深度重构方案

## 1. 用户反馈的四大核心痛点分析

### 痛点 1：为何弹窗显示“暂无配额重置记录”？
- **原因**：之前的重置检测逻辑只在“探测数据从消耗态（如 10%）再次被探测且发生回满跃迁”这一瞬间才会写入历史记录。对于历史已有账号，如果没有在运行新逻辑期间经历一次完整的“消耗 ➔ 刷新回满”，数据库表中尚无增量事件产生。
- **改进**：首次接入/启动时，对已有快照做一次智能基线补全；若当前快照本就处于重置后状态（结合已有 `resetAtMs` 和 `capturedAt` 推断），生成初始状态。

### 痛点 2：实际重置时间点的推断（非探测时间点）
- **场景**：例如 18:00 用完了（5h 滚动窗口），原定自然重置是 23:00。用户在 23:00~24:00 之间一直没有发起过使用，窗口停在 100%。当用户在 24:00 打开 WebUI 进行刷新探测时，探测时间是 24:00。
- **问题**：旧逻辑把“发现时间（24:00）”直接当成了“重置时间”。
- **改进**：
  - 对于**自然周期重置 (`natural / cycle_rollover`)**：实际重置发生的物理时间点正是原定预期的 **`previousExpectedResetAtMs` (23:00)**，而不是晚来探测的 `24:00`！
  - 必须记录真实发生的物理预估时间：`occurred_at_ms = previousExpectedResetAtMs`；
  - `detected_at_ms` (24:00) 仅作为观测发现时间，前端主展示必须使用 `occurred_at_ms`（即 23:00 重置）。

### 痛点 3：额度用量刷新后持续记录 latest 值并覆盖最新基线
- **机制**：
  - 每次探测后，原子更新 `account_quota_detector_state` 表的最新值 (`last_remaining_pct`, `last_expected_reset_at_ms`, `last_captured_at_ms`)；
  - 保证多维度（5h, 7d, 30d, model）各自独立拥有精确的 latest 基线；
  - 下次无论从 WebUI、CLI、网关还是后台定时探测进入，都基于最新的 latest 状态进行比对计算并覆盖更新。

### 痛点 4：AIH Server 内部异步自动探测并持久化
- **现状**：目前后台缺少常态化的自动配额探测轮询，导致如果用户长时间不手动点“刷新”，就无法在 23:00 附近及时感知额度恢复，全靠用户在 24:00 甚至第二天手动刷新。
- **改进**：在 `aih server` 内部增加轻量级 **Account Quota Auto-Probe Scheduler**（例如针对已消耗/待重置的 OAuth 账号，在其临近 resetAtMs 或定期做异步自动探测并写入快照），从源头消除时间误差。

# session-A 报告：native session chat 纯构造层迁 Go

分支：`slice/session-wt`（基线 `main @ 65555ab7`，未 push）
范围：`lib/server/native-session-chat-*.js`、`native-chat-run-*.js`、`session-*.js`（不含 activity/task 线）、Go 侧 `internal/runtime/providercli`

## 结论

1. 「一次 Chat 请求 → 某 CLI 原生会话命令」的纯构造逻辑已迁到 Go：
   `internal/runtime/providercli/sessionchat`（命令构造、传输描述符、环境投影、
   失败分类、session 续接参数、tmux shell 组装）。
2. 对拍快照 517 例，Go 表驱动测试逐字段全等；Node 现有用例
   `test/native-session-driver-auto-continue.test.js` 5/5 通过。
3. `go build ./...`、`go test ./...`、`go vet` 均通过。
4. **Node 侧一行未改**，当前是「Go 有等价实现、Node 仍是唯一在读的一方」。切读方案见第 5 节。
5. 为让 `go build ./...` 通过，补了基线缺失符号
   `nativeaccount.SanitizeClineProvidersDocument`（见第 7 节，与本切片可拆分提交）。

## 1. 盘点：一次 Chat 请求如何变成 CLI 原生命令

Node 侧的完整链路（`lib/server/native-session-chat.js#spawnNativeSessionStream`）：

| 阶段 | 事实来源 | 输入 → 输出 |
| --- | --- | --- |
| 传输形态 | `native-session-chat-transport.js` 的 `TRANSPORT_BY_PROVIDER` | provider + 是否续聊 → `headless-stream / pty-transcript / acp-session / desktop-session`、prompt 投递方式、`streamUsage`、`tmuxRun` |
| 命令构造 | `native-session-chat-command.js#buildStartCommand/buildResumeCommand` | provider + prompt/sessionId/model/图片/交互式/projectPath/opencode 布局 → `{commandName,args}` 或稳定错误码 |
| 账号目录参数 | `applyProviderConfigDirArgs` | provider → 合同里的 `configDirFlag`（当前仅 qoder/qodercn 的 `--config-dir`） |
| 环境投影 | `native-session-chat-env.js` + `provider-runtime-env.js` | provider + 账号 env + 投影目录 + 宿主 env → 运行目录 / 是否投影原生凭据 / 最终 env |
| 工作目录 | 路由层 `projectPath` + 布局表 | codex `-C`；opencode v1 `--dir`、v2 由 `PWD/cwd` 表达；tmux run 另有 `cwd` |
| 失败分类 | `native-session-chat-failure.js` | 错误对象/终端输出 → `{code,message,retryAnotherAccount}` 或账号运行态阻塞 |
| 会话恢复 | 命令构造 + `session-reader` | gemini `--session-file`（绝对路径，绕开 cwd 发现）或 `--resume`；claude/codex/qoder/grok/agy/opencode/cline 各自的续接旗标；家族 IDE 会话拒绝续接 |
| 进程包装 | `native-run-tmux.js` | runId/logPath/argv → socket 名、`sh -c` 命令串、退出标记 |

Go 包的边界：**不做 I/O**。Node 侧需要读盘/探测的输入全部改为参数注入：

- opencode 布局：`ResolveOpenCodeLayout(envValue)` 只处理 env 钉选与默认值，`--help` 探测留在 Node。
- gemini 会话文件：Go 接收 `GeminiSessionFile`（调用方已 stat 过的绝对路径）。
- claude 图片：Go 接收 base64 数据，读文件与编码留在 Node。
- tmux 可用性、当前时间、平台：显式参数。

## 5. 下一步：Node 如何切读

当前 Node 仍是唯一读取方。建议按「影子 → 单 provider 翻转 → 全量」三步：

1. **暴露 Go 纯函数**：新增管理端点（沿用 `go-core-host` + `go-management-client` 的既有模式），
   例如 `POST /v1/management/native-session-command`，请求体只含已解析输入
   （provider、prompt、sessionId、model、imagePaths、interactiveCli、projectPath、
   已解析的 sessionPath/geminiSessionFile、opencode layout id、platform），响应
   `{commandName,args}` 或 `{error:{code,message}}`。不要在 Go 端点里读会话文件或探测 CLI。
2. **Node 适配器**：新增 `lib/server/native-session-chat-command-go.js`，只做
   「Node 输入 → HTTP → 形状转换」，超时/非 2xx/解析失败一律回退 Node 现有函数。
3. **影子期**：`spawnNativeSessionStream` 同时调用两侧，仅用 Node 结果；不一致按
   provider + 是否续聊计数并采样日志（不打印 prompt/env 明文）。跑满一个发版窗口后按
   provider 白名单翻转。
4. **翻转顺序建议**：claude → codex → opencode → qoder/qodercn → 家族四支 → cline →
   grok → agy → gemini。zcode 走桌面会话 runner，不进这批。
5. **环境投影先只切 gemini/claude 的纯段**：即 `BuildProjectedEnvironment` 的基座与
   gemini 接入点；其余 Provider 的 env 仍由 Node `buildProviderRuntimeEnv` 的
   `buildEnvPatch` 产出（见下节缺口），不要整段替换。

## 6. 剩余缺口（未迁/未覆盖）

### 6.1 环境（最大缺口）

- `launch-profile` 的 13 家 `buildEnvPatch`：各 Provider 的配置模板、`-P` 槽位、
  `OPENCODE_CONFIG`、`CLINE_*`、kimi/zcode 沙箱变量等，全部仍在 Node。
- `prepareProviderRuntime`：原生凭据文件物化、MCP 资源对账、aih-collab skill 安装。
- 账号 env 选择：`loadAccountEnv/loadProviderAccountEnv`、claude relay、codex gateway
  connection、`shouldRelayClaudeAccount`；Go 只接收已经选好的 `AccountEnv`。
- `buildProviderRuntimeEnv` 的尾部：跨 Provider 协作变量、codex managed-launch 标记、
  模型别名改写、`PATH` 归并、UTF-8 locale 归一、代理归一/本机网关绕过、出口代理守卫。
- 账号运行态写入（`recordNativeAccountRuntimeBlocker/Success`、门禁/hub/服务、恢复判定）；
  Go 只迁了分类与运行态结构。

### 6.2 命令与编排

- zcode 桌面会话通道（`spawnZcodeDesktopSessionStream`）与 `desktop-session` 执行体。
- ACP：`buildAcpEntryArgs`、`resolveAcpAuthMethod`、`acp-session-runner`；Go 只声明了
  cline 的 `resumeMode=acp-session`。
- 审批模式参数（`grokApprovalArgs` 等）、codex `injectCodexProviderArgs`、
  claude `buildClaudeLaunchSettingsArgs`、cline `-P` 槽位。
- agy 暖机池快路径（`agentapi send-message`）与模型一致性 gate。
- CLI 解析：`resolveNativeCliLaunch`（workbuddy 内嵌运行时、claude `cli.js`、
  `PATH/runtime-tools` 探测）、安装预检。

### 6.3 I/O 与存储

- `native-session-chat-sessions.js`：claude/codex/gemini/agy 会话文件枚举、codex
  `state.db` 推断、cline `sessions.db`、创建后 sessionId 回认。全部是文件/SQLite I/O。
- `native-chat-run-persistence.js / native-chat-run-store.js / native-chat-run-artifact-store.js`：
  run 事件落盘、内存表、artifact 外置。属于进程状态与磁盘，不是命令构造。
- `native-session-chat-launch.js`：CLI 就绪检查与安装进度。

### 6.4 平台与边界

- Windows 私有区字符路径还原（`decodeEncodedWindowsPath`）未迁；调用方传已还原路径。
- Windows 系统代理（`applyWindowsSystemProxy`）未迁。
- claude 的 win32 分支无法在 darwin 上做 Node 对拍，已用 Go 单测
  `TestClaudeStreamJSONInputWindowsFallback` 覆盖（含 `windows→win32` 归一）。
- 快照中的 JSON 对象键顺序：Go `encoding/json` 对 map 排序；行为等价但字节序与
  Node `JSON.stringify` 不同。仅影响逐字节比较，不影响语义；如后续要求字节级一致，
  需要在 Go 侧用有序结构重建 cline 文档。

## 7. 基线缺失符号的处理（可拆分）

`internal/adapters/accounts/deletionprojection/credential.go:540` 引用了
`nativeaccount.SanitizeClineProvidersDocument`，但该函数在基线中不存在，导致
`go build ./...` 直接失败。它属于 cline 删除投影切片，不属于 session chat；为满足
验收，本次按 Node `lib/account/cline-credentials.js#sanitizeClineProvidersDocument` 的
规则补了实现与 3 条单测：

- 只保留 `cline`/`cline-pass` 两个槽位，丢掉其它 Provider 的明文密钥；
- `auth.expiresAt` 字符串 → 毫秒数字（CLI 会把字符串判成未登录）；
- `version` 数字归一、`lastUsedProvider` 限定在槽位内、`modes` 原样保留。

如果评审希望严格按切片提交，可把 `nativeaccount/cline_document*.go` 单独 cherry-pick
给 cline 投影线，本切片的其余文件不依赖它（只是构建验收需要）。

- 远程 shell：四种认证的完整 argv、私钥换行补齐、0600/0700、密码不进 argv、askpass 内容、会话名收敛与 60 字符截断、凭据覆写后删除。

- 剪贴板：参数/远端参数、带空格的引用、Alt+V 与 Ctrl+V 的 ESC/CSI-u/modifyOtherKeys 编码、bracketed paste。

已知语义差异（均为边界，不影响主流程）：

1. 目录排序：Node 用 `localeCompare`，Go 用 `strings.Compare`（字节序）。中文/重音文件名顺序可能不同；要完全一致需引入 `golang.org/x/text/collate`，本次按「不加依赖」未做。
2. `ProbeSSHTarget` 对空白 `user` 按空处理；Node 的真值判断会把单个空格当成用户名。
3. `BuildRemoteShellCommand` 对负数端口回退 22；Node 会原样传 `-1`。属无效配置。
4. PowerShell 编码对孤立代理项（非法 UTF-8 已在上游被替换）与 Node 的 UTF-16 行为略有差异。

## 5. 接线方案（Node 保持不变时）

按能力从易到难：

1. **身份文件校验**：在 Go HTTP 路由或配置写入路径调用
   `sshhost.ResolveIdentityFilePath`，把 `IdentityFileError.Code` 直接映射到现有 400 响应的
   `reason`（文案表见 `webui-ssh-host-routes.js:25-32`）。
2. **连通性探测**：`POST /v0/webui/ssh-connections/test` 改调 `ProbeSSHTarget`；
   `ProbeOptions.Runner` 默认就是 spawn `ssh`，返回结构与现有 JSON 字段一一对应。
3. **目录浏览**：给 `BrowseMachine` 写一个适配器，包住
   `getRemoteWorkspaceService(...).machine(connectionId)`；`Profile` 映射 `facts.home` /
   `facts.dialect.id`，`Exec` 映射 `machine.exec(cmd, {timeoutMs, lane:'interactive'})`。
4. **工作区终端**：`BuildRemoteShellCommand` 产出 `Command{File,Args,Env,TempFiles}`；
   外层 PTY/tmux 生命周期仍在 Node/Go 宿主层，启动前合并环境变量，退出后调用
   `RemoveCredentialFiles`。
5. **守护**：`__remote_ws__` 子命令改调 `Supervisor.Run(ctx)`。需要两个适配器：
   - `WorkspaceReader`：读 SQLite `app_kv` 的 `ssh_workspaces` / `ssh_connections`（目前 Go 侧
     没有 app_kv 读取器，见缺口 G1）；
   - 信号：把进程收到的 SIGTERM/SIGHUP 转成 `context.CancelFunc`（Node 是直接转发给子进程）。
6. **主机指纹**：若 Go 接管拨号，用 `HostKeyStore` + `x/crypto/ssh` 的 `HostKeyCallback`；
   仓库可先实现为读写同一个 `ssh_known_hosts` JSON，避免 Go/Node 两套 TOFU 状态分叉。

## 6. 剩余缺口

**G1. app_kv 读取器（阻塞守护接线）**：`WorkspaceReader` 只有接口与内存 fake，Go 侧尚无
SQLite `app_kv` 访问层。方案：新增只读适配器（`modernc.org/sqlite` 已在 go.mod）读
`SELECT value FROM app_kv WHERE key=?`，JSON 解到 `[]Workspace` / `[]Connection`；
损坏数据按「未配置」处理，与 `readJsonValue` 的宽松语义一致。

**G2. 真正的 SSH 客户端（远程工作区通道层）**：连接池、lane 限流、SFTP、断线健康检查、
出网代理与反向隧道仍在 Node 的 ssh2 上。迁 Go 必须引入 `golang.org/x/crypto/ssh`
（见第 8 节），并重写 `lib/remote-workspace/**`；本包只提供它需要的纯逻辑。

**G3. 图片粘贴桥**：本次只迁了参数解析、远端参数引用与按键识别。未迁：
OSC 5379 帧编解码（`frames.js`）、shim 协议（`shim-protocol.js`）、图片校验/规范化
（`image-data.js`、`image-normalizer.js`）、本机剪贴板读取（`clipboard.js`、
`terminal-clipboard.js`）、远端探针（`terminal-probe.js`）、`inbox.js` 与 `clip-agent*`。
这些依赖宿主剪贴板工具与 PTY 桥，不是 SSH 协议本身，建议单独切片。

**G4. known_hosts 文件路径**：解析器已就绪，但未接 `~/.ssh/known_hosts` 的默认路径、
文件监视与 `known_hosts2`。Node 现在用 app_kv TOFU 而不是 OpenSSH 文件，需要先决定
Go 接管后以哪边为准（建议双写过渡）。

**G5. 守护的信号语义**：Node 在 supervisor 进程上监听 SIGTERM/SIGHUP 并转发给 ssh 子进程；
Go 版只响应 `ctx` 取消。接线时必须把 OS 信号桥接到 cancel，否则 tmux 杀会话时 ssh 可能
残留到远端超时。

**G6. 探测与 TOFU 的口径**：探测走 `ssh` CLI 的
`StrictHostKeyChecking=accept-new`，会绕过 app_kv 指纹；Node 现状相同。若要求统一信任模型，
探测应改用 Go SSH 客户端 + `HostKeyStore`。

## 8. `x/crypto/ssh` 依赖评估

结论：**不 blocked**。`go.mod` 已有 `golang.org/x/crypto v0.51.0`（indirect），`go.sum`
有校验和，模块缓存中存在 `ssh`、`ssh/agent`、`ssh/knownhosts`。本次没有 import 它，
因此 `go.mod` 未变。

必须依赖它的能力（仅当这些能力迁 Go 时）：

| 能力 | 需要的包 |
| --- | --- |
| 真实拨号、认证（agent / 私钥 / 密码 / keyboard-interactive） | `golang.org/x/crypto/ssh`、`ssh/agent` |
| 主机公钥校验回调 | `golang.org/x/crypto/ssh`（消费本包的 `HostKeyStore` / `MatchKnownHost`） |
| 远程命令通道、PTY 请求、窗口变更 | `golang.org/x/crypto/ssh` |
| SFTP 文件操作 | `github.com/pkg/sftp`（**go.mod 没有**，真要做文件通道需新增依赖或改用 `ssh` CLI/SFTP 子系统） |
| 本地/远程端口转发（出网代理、反向隧道） | `golang.org/x/crypto/ssh` 的 `Client.Dial` / `Listen` |

不需要 x/crypto/ssh 的：本包全部内容（含 known_hosts 解析与 HMAC-SHA1 哈希主机名匹配，
均用标准库实现）、CLI 探测、命令构造、状态机。

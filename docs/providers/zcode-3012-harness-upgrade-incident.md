# 事故记录：ZCode 客户端升级导致 relay 全线 3012（2026-10-31）

## 摘要

| 项目 | 内容 |
| --- | --- |
| 发现时间 | 2026-10-31 01:22 起（WebUI chat 多个 zcode 会话卡在 `running`） |
| 影响面 | zcode 全部推理通道：relay（`/v1/messages`、chat harness）、`aih zcode -p`（app-server） |
| 用户可见现象 | 请求全部 `HTTP 405 {"code":3012,"msg":"request has been blocked due to unusual activity."}`；失败前还要排队 ~5.4s（relay pacing），体感「又慢又错」 |
| 根因 | 客户端 3.17.1 改了 harness 的 identity 行，学习钩子按**字面文案**匹配 → 缓存不再更新 → relay 持续发旧 harness，且版本号来自另一处（本地推断），两者错配 |
| 是否账号问题 | 不是。同一账号同一时刻官方桌面端正常出答案；`3009` 才是并发上限，`3012` 是准入拒绝 |
| 状态 | 已修复并真机验证 |

## 根因（三条，缺一不会炸）

1. **把厂商文案当成 API**：`HARNESS_IDENTITY_MARKER = 'You are ZCode, an interactive coding agent'`
   用 `startsWith` 匹配。客户端改一句话，学习链路当天静默失效。
2. **画像被拆成两个来源**：harness 来自桌面端（跟着升级变），版本号来自本地推断
   （安装页/缓存/种子，没跟着变）。两个一配就错位。
3. **失败是静默的**：解析不到就 `return`，不写日志、不告警、不标记失效 —— 整个事故期间
   零痕迹，只能人肉抓包定位。

## 关键证据：上游认的是「成对」，不是「最新」

同一账号、同一时刻、9s 间隔的四格矩阵（harness 取自 10-28 抓包与 10-31 抓包）：

| app_version | harness | 结果 |
| --- | --- | --- |
| 3.16.3 | 42/3155/8672（3.16 版） | **200** |
| 3.17.1 | 42/3155/8672（3.16 版） | 405 3012 |
| 3.16.3 | 35/3173/1703（3.17.1 版） | 405 3012 |
| 3.17.1 | 35/3173/1703（3.17.1 版） | **200** |

⇒ **没有「必须升到 X 版本」的门槛**，旧客户端 + 旧 harness 照样放行。任何单方面的
「把版本号抬上去」只会制造错配，必然 3012。

## 修复

### 1. harness 识别改成形状判据（版本无关）

`lib/server/zcode-harness-store.js`：≥2 个文本块 + 首块 ≤200 字符 + 其余合计 ≥500 字符。
不匹配任何文案；客户端自己的 system（通常一整段长文本）不满足，仍会被 relay 替换。

### 2. 画像成对版本化

缓存单位从「一份 harness」改成 `profile = { appVersion, blocks }`：

- **学**：`appVersion` 取自那条请求自己的 `x-zcode-app-version` 头（不是启动配置），和 `system` 一起落盘；
- **发**：relay 与 `-p` 都从同一份画像里同时取版本号和 harness，代码里不存在第二个版本来源；
- **历史**：保留最近 5 份，客户端升级/回滚都能命中；
- **回退**：某份被 405 拒就标记失效，下一次请求自动退到上一份。

### 3. 失败不再静默

- 学习不到 harness → 打 warn（按版本去重）；
- 画像版本与发送版本不一致 → 打 warn（正常情况永不触发，触发即说明有人把来源拆开了）。

### 4. `aih zcode -p` 纳入同一份画像

新增 `lib/runtime/zcode-outbound-profile.js`，以 `--require` 预加载进 CLI 子进程，
把 plan 请求的 `x-zcode-app-version` / `user-agent` 与 `system` 成对换成缓存画像。
此前它自报 CLI bundle 版本 `0.17.1` + 自带旧 system，稳定 3012。

### 5. 删掉版本下限

上一版曾加 `MIN_ZCODE_APP_VERSION = '3.17.0'` 兜底，**已删除**：矩阵证明它会主动制造
错配，而且下次客户端再升级这个常量只会变成新的谎言。

## 教训

- **厂商的提示词/文案不是 API**。任何「按字符串匹配客户端身份」的实现都会在某个版本静默失效。
- **成对出现的东西必须成对存取**。拆开取源 = 定时炸弹，而且失败信息（3012）指向「风控」，误导性极强。
- **静默降级是最贵的失败模式**。同一条链路如果有日志，这次定位成本是分钟级而不是小时级。
- 客户端的「新」不天然等于「对」。判断依据应该是「这份组合有没有被上游放行过」，而不是版本号大小。
